## Критические уязвимости безопасности

### 1. Утечка правильных ответов клиенту при старте попытки

**Файл:** `Exerciser.WebApi/Controllers/AttemptsController.cs`, `StartAttemptResponse`, `QuestionSnapshotDto`

При создании попытки (`POST /api/v1/attempts`) сервер возвращает `QuestionSnapshotDto`, содержащий поле `CorrectAnswers` — массив правильных ответов на каждый вопрос. Это позволяет студенту увидеть правильные ответы до прохождения теста.

**Рекомендация:** Удалить поле `CorrectAnswers` из `QuestionSnapshotDto` и `StartAttemptResponse`. Правильные ответы должны храниться только на сервере и использоваться исключительно при проверке.

### 2. Клиентский подсчёт баллов

**Файлы:** `Exerciser.WebApi/Controllers/AttemptsController.cs`, `FinishAttemptRequest`, `Exerciser.FrontEnd/Student/src/views/AttemptView.vue`

Баллы за попытку рассчитываются на клиенте и принимаются сервером «как есть» через `FinishAttemptRequest`. Студент может отправить любое значение `Score` без реального прохождения теста.

**Рекомендация:**
- Удалить поле `Score` из `FinishAttemptRequest` и `AnswerSubmissionDto`.
- Реализовать серверный подсчёт баллов в `AttemptsController.Finish()`: сравнивать ответы студента с эталонными, хранящимися на сервере.

## Проблемы высокого приоритета

### 3. Дублирование кода (DRY)

**Backend:**
- `ExamsController` и `AttemptsController` содержат идентичную логику получения экзамена с вопросами.
- Расчёт максимального балла дублируется в нескольких местах (`Questions.Sum(q => q.MaxScore)`).

**Рекомендация:** Вынести общую логику в extension-метод (например, `GetMaxScore()`) или отдельный сервис.

**Frontend (админ-панель):**
- Функции `getTypeIcon` и `getTypeLabel` дублируются в `teacher.js`, `edit.js` и `create.js`.

**Рекомендация:** Вынести в общий утилитарный файл и импортировать во всех скриптах.

### 4. CI/CD пайплайн не работает

**Файл:** `.github/workflows/ci_cd.yml`

В workflow указано неверное имя solution-файла — сборка падает на шаге `dotnet build`.

**Рекомендация:** Исправить имя solution-файла в workflow на актуальное.

### 5. Примитивные типы вместо доменных

**Файл:** `Exerciser.WebApi/Models/`

Типы вопросов (`QuestionType`) хранятся как `string` вместо `enum`. Это приводит к:
- Опечаткам без ошибок компиляции.
- Разбросанным строковым литералам по коду.

**Рекомендация:** Заменить `string QuestionType` на `enum QuestionType` с конвертацией на уровне БД/сериализации.

### 6. Неиспользуемый код во фронтенде

**Файл:** `Exerciser.FrontEnd/Student/src/components/HelloWorld.vue`

Стандартный компонент из Vue CLI шаблона, не используется в приложении.

**Рекомендация:** Удалить `HelloWorld.vue` и связанные ассеты.

### 7. Отсутствует обработка ошибок для API-метода

**Файл:** `Exerciser.FrontEnd/Student/src/api.js`

В `AttemptView.vue` вызывается метод `getAttemptExam`, который отсутствует в `api.js`. При вызове произойдёт runtime-ошибка.

**Рекомендация:** Добавить недостающий метод в `api.js` или исправить вызов.

## Проблемы среднего приоритета

### 8. Жёсткая зависимость от Redis

**Файл:** `Exerciser.WebApi/Services/DistributedCacheService.cs`

Сервис кеширования жёстко завязан на Redis. При локальной разработке это требует поднятия Redis-контейнера.

**Рекомендация:** Использовать `IMemoryCache` как fallback при отсутствии Redis, либо абстрагировать через `IDistributedCache`.

### 9. Перегруженный `Program.cs`

**Файл:** `Exerciser.WebApi/Program.cs`

Вся конфигурация сервисов собрана в одном файле, что затрудняет чтение и поддержку.

**Рекомендация:** Вынести конфигурацию в extension-методы по зонам ответственности (`AddDatabase()`, `AddSwagger()`, `AddCaching()` и т.д.).

### 10. Дублирование DTO

**Файлы:** `Exerciser.WebApi/DTOs/QuestionDto.cs`, `Exerciser.WebApi/DTOs/QuestionSnapshotDto.cs`

`QuestionDto` и `QuestionSnapshotDto` практически идентичны. Снэпшоты созданы для изоляции попыток от изменений вопросов, но это усложняет код.

**Рекомендация:** Оценить необходимость снэпшотов. Возможная альтернатива — deep copy с AutoMapper.

### 11. Хардкод API base URL в админ-панели

**Файл:** `Exerciser.FrontEnd/Admin/views/includes/config.pug`

Базовый URL API захардкожен, что усложняет развёртывание в разных окружениях.

**Рекомендация:** Использовать переменные окружения или относительные пути.

### 12. Устаревшая документация

**Файлы:** `README.md`, `docs/API_EXAMPLES.md`

- `README.md` упоминает несуществующие тесты.
- `API_EXAMPLES.md` демонстрирует возврат правильных ответов клиенту (уязвимость №1).

**Рекомендация:** Актуализировать документацию после исправления уязвимостей.

### 13. Минимальное покрытие тестами

В проекте обнаружено всего 3 юнит-теста, покрывающих базовый сценарий.

**Рекомендация:**
- Добавить unit-тесты для контроллеров, сервисов и middleware.
- Добавить интеграционные тесты с Testcontainers (PostgreSQL + Redis).
- Добавить тесты фронтенда (Vue Test Utils).
- Покрыть граничные случаи (пустые ответы, невалидные ID, таймауты).

### 14. Неоптимальная работа с Docker

**Файл:** `Exerciser.WebApi/Dockerfile`

Dockerfile настроен хорошо (multi-stage build), но:
- Отсутствует `.dockerignore`.
- Нет Docker Compose для локальной разработки (front + back + DB).

**Рекомендация:** Добавить `.dockerignore` и `docker-compose.yml` для локальной разработки.

## Сильные стороны проекта

1. **Чёткое разделение слоёв:** Контроллеры → Сервисы → Репозитории → EF Core. Хорошая архитектура в стиле Clean Architecture.

2. **Валидация через FluentValidation:** Все входящие DTO имеют строгую валидацию, что предотвращает некорректные данные на входе.

3. **Глобальная обработка ошибок:** Присутствует middleware для перехвата исключений и формирования единообразных ответов.

4. **Docker-готовность:** Приложение легко контейнеризируется и готово к деплою.

5. **Качественная документация:** Подробный README, CHANGELOG, инструкции по настройке Postman и примеры API-запросов.
